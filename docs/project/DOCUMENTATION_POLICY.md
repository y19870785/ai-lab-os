# 仓库文档政策（Documentation Policy）

## 1. 目的与适用范围

本政策适用于 AI-Lab OS 仓库中由 Git 跟踪、且由本仓库维护的全部 Markdown 文档，
包括根目录文档、项目治理文档、架构文档、RFC、ADR、验收记录、发布说明、GitHub
模板以及代码目录中的说明文件。

仓库自有 Markdown 文档以简体中文作为唯一主要叙述语言。英文仅用于代码、技术标识、
标准名称、产品名称和必须保持原样的证据。

中文主要叙述语言不等于禁止所有英文。普通读者应当能够仅依靠中文理解标题、说明、
规则、结论、限制、操作步骤和治理状态。

## 2. 必须使用中文的内容

以下内容必须以简体中文为主：

- 文档主标题与章节标题；
- 普通说明段落；
- 表格列名和解释性单元格；
- 提示、警告与注意事项；
- 操作步骤与验收说明；
- RFC、ADR、SP、ACC 的背景、目标、决策、后果和非目标；
- README、架构、贡献、安全、发布和治理说明；
- Issue、PR 与 Review 模板中的用户提示；
- Changelog 中描述产品变化的普通叙述；
- 历史文档中用于解释事实的叙述。

## 3. 必须保留技术形式或原文的内容

以下内容不得为了中文化而随意翻译：

- fenced code block 与 inline code；
- 可执行命令、API 路径和 HTTP 方法；
- 类、函数、模块、包、字段和参数名；
- 环境变量、配置键和值；
- 数据库、表和列名；
- 文件名、仓库路径、Branch、Commit SHA、PR、Issue 与 Workflow Run；
- RFC、ADR、SP、ACC 标识符；
- 版本号、Tag、Release 名称和机器状态值；
- 标准、协议、产品与库的正式名称；
- 原始错误信息、日志、外部证据以及历史 Commit 或 PR 标题；
- JSON、YAML、TOML、PowerShell、Bash、Python 与 SQL 示例。

原始错误、日志和标题证据应放在代码块或反引号中，并由中文说明交代来源与含义。

## 4. 标题、章节、表格与提示

每个仓库自有 Markdown 必须有且只有一个明确的一级标题，一级标题必须包含中文。
RFC、ADR、SP、ACC、API、CLI 和产品名可作为技术标识保留。

章节标题必须包含中文；括号内可以补充稳定英文术语。表格的解释性列名和内容使用中文，
纯技术标识列可以保留原文。提示和警告必须先用中文说明影响，再引用原始技术内容。

## 5. 术语首次出现与后续用法

技术英文第一次出现在普通叙述中时，优先使用“中文名称（English Term）”。后续统一使用
已登记的中文名称、技术缩写或代码标识，不得在同一文档中反复改变译法。

跨文档术语以
[统一术语表](TERMINOLOGY_GLOSSARY.md) 为准。类型名、字段名和公开 API 不受普通叙述
译名替代。

## 6. RFC、ADR、SP 与 ACC 模板

- RFC：中文说明问题、目标、方案、边界、风险、停止条件和治理状态；
- ADR：中文说明背景、决策、后果、替代方案和治理状态；
- SP：中文说明产品范围、实施阶段、授权边界和非目标；
- ACC：中文说明前置条件、操作步骤、证据、失败分类与场景状态。

`Status`、`PASSED`、`FAILED`、`NOT_EXECUTED` 等机器状态保留原值。规划基线不得写成
产品实现，自动化验证不得写成人工验收。

## 7. 当前事实与历史事实

当前机器治理状态以根目录 `project_state.json` 为权威来源。人工文档引用当前状态时应
尽量链接或概括，不应在大量文档复制整段易漂移状态。

历史 SHA、PR、日期、验收计数和原始结论属于证据，不得因翻译而更改。无法确认的历史事实
必须保留并报告为 `UNRESOLVED_DOCUMENTATION_FINDING`，不得猜测或删除。

## 8. 文件命名与重命名

英文文件名、RFC/ADR 编号和稳定路径属于技术标识。中文化默认不重命名现有文件。
只有明确拼写错误、重复文件或失效路径才可提出重命名建议；大规模重命名必须单独审查。

## 9. 排除项管理

第三方原样文档、自动生成文档、外部许可证或法规原文，以及必须保持英文的测试 fixture
可以排除。任何排除项都必须同时：

1. 出现在 [Markdown 文档清单](MARKDOWN_INVENTORY.md)；
2. 标明所有权、排除原因和最终状态；
3. 出现在语言治理测试的集中式 allowlist；
4. 由审查者确认没有借排除规避中文化。

不得使用目录级宽泛排除掩盖仓库自有文档。

## 10. Markdown 链接与锚点

仓库内链接使用相对 POSIX 路径。链接目标必须存在；目录链接应明确指向入口文档。
外部链接必须使用完整 `https://` 或其他明确协议。纯页内锚点不作为文件路径检查，
但标题变更时必须人工确认锚点引用。

文件名含空格或特殊字符时应使用合法 URL 编码。不得在同一相对链接中混用 Windows
反斜杠与 POSIX 斜杠。

## 11. 新增文档审查

新增 Markdown 必须在同一变更中：

- 更新 Markdown 文档清单；
- 使用包含中文的一级标题和章节标题；
- 遵循统一术语；
- 验证相对链接；
- 明确当前事实与历史事实来源；
- 通过 Markdown 语言与链接治理测试。

## 12. 自动门禁的边界

自动门禁使用确定性启发式检查清单完整性、中文一级标题、纯英文长段落、未完成翻译标记和
相对链接。它不理解语义，也不能证明翻译质量或历史事实正确。

自动门禁通过后仍必须进行人工审计，包括术语一致性、代码块与命令保持、历史证据精度、
文档职责和治理状态一致性。
